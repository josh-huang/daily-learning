防范与治理“Context Rot”（上下文腐烂），正是 Context Engineering 最核心、最长期的任务之一。如果把 Prompt Engineering 比作“写好单次指令的艺术”，那么 Context Engineering 就是“管理整个上下文系统的工程学”。在这个系统里，Context 是动态增长、不断演化的，如果不加干预，它必然会走向“腐烂”。🔍 什么是 Context Rot（上下文腐烂）？随着对话轮次增加、Agent 链条拉长或 RAG 检索结果堆积，Context Window（上下文窗口）内部会产生各种“病态现象”：信噪比（SNR）急剧下降：不相关的历史对话、废话、长文本片段挤占了有效注意力空间。中间遗忘（Lost in the Middle）：Transformer 的 Self-Attention 机制天然偏向开头和结尾，中间夹杂的关键信息容易被模型忽略。陈旧与冲突信息污染（Stale/Conflicting Context）：早期的旧设定、过期的临时变量或上一轮产生的幻觉/错误输出留在 Context 中，导致模型在后续推导中“被带偏”或产生逻辑矛盾。延迟与成本飙升：长 Context 带来庞大的 Time-to-First-Token (TTFT) 延迟与无意义的 Token 消费。🛠️ Context Engineering 如何预防 Context Rot？Context Engineering 的本质，就是为 LLM 建立一套内存管理与垃圾回收机制（Garbage Collection）。常用的对抗手段包括：1. 动态剪枝与滑窗（Pruning & Windowing）滑动窗口：丢弃过于久远的边缘对话，只保留最近 $N$ 轮的核心上下文。选择性剪枝：通过算法剔除冗余的系统日志、中间思考过程（如 Thinking/Reasoning 标签里的中间步骤），只向后续步骤传递关键结论。2. 状态压缩与摘要（Summarization & Compression）增量摘要（Incremental Summarization）：当对话达到一定长度时，由后台异步调用模型将老旧上下文压缩为简短的“系统状态报告（State/Memory）”。语义压缩算法：利用如 LLMLingua 等工具对不影响语义的 Token 进行算法级剔除。3. 上下文重排与结构化（Re-ranking & Structuring）逆转“Lost in the Middle”：将最关键的 System Prompt、工具定义或重度依赖的依据，放在 Context 的最前或最后。XML / Markdown 语义分隔：利用清晰的标记语言（如 <context>、<history>、<retrieved_docs>）分隔不同来源的信息，帮助模型精准定位权重。4. 显式纠错与状态重写（State Mutation）在 Multi-Agent 或复杂的 Tool-use 流程中，一旦发现上一步报错或产生无效输出，Context Engineering 会在将结果写入历史之前进行清洗与纠错，防止错误上下文在未来的循环中被放大。总结没有 Context Engineering，模型的上下文就像长期不清理的电脑内存，最终必然因为 Context Rot 导致表现滑坡、逻辑混乱；而良好的 Context Engineering 能让模型在处理几十万 Token 的超长任务时，依然保持初始状态般的清晰与敏捷
